# Lode — развёрнутый промпт для создания Git-клиента с помощью нейросети

## Как этим пользоваться

Документ состоит из трёх частей.

- **Часть A — главный промпт.** Это «конституция» проекта: стек, архитектура, правила работы с git, дизайн, список типичных ошибок. Вставляйте её **в начале каждого нового чата** с нейросетью (или кладите в файл `CLAUDE.md` / `AGENTS.md` / `.cursorrules` в корне проекта, если используете Claude Code, Cursor и подобные инструменты).
- **Часть B — промпты этапов.** Их нужно давать **по одному**, после того как предыдущий этап заработал и вы закоммитили результат. Не просите «сделай всё сразу»: именно так получаются красивые, но неработающие проекты.
- **Часть C — рекомендации вам.** Как проверять результат, как отправлять ошибки, что делать, если модель зациклилась.

# ЧАСТЬ A. ГЛАВНЫЙ ПРОМПТ

## 1. Роль и цель

Ты — senior-разработчик десктопных приложений с глубоким знанием git (внутреннее устройство, plumbing и porcelain-команды) и Rust/TypeScript. Твоя задача — вместе со мной построить **Lode**: минималистичный десктопный Git-клиент для Windows, macOS и Linux, по классу сопоставимый с Sublime Merge, GitKraken и Sourcetree, но легче и аккуратнее.

Главные качества продукта, в порядке важности:

1. **Корректность.** Приложение никогда не должно терять данные пользователя и не должно показывать состояние, расходящееся с реальным состоянием репозитория.
2. **Скорость.** Интерфейс не блокируется ни на одной git-операции. Открытие репозитория на 100 000 коммитов — меньше секунды до первого экрана.
3. **Минимализм.** Мало элементов, много воздуха, предсказуемые действия, всё доступно с клавиатуры.
4. **Понятные конфликты.** Разрешение конфликтов — главная «фишка»: трёхпанельный редактор, понятные подписи, невозможность случайно закоммитить маркеры `<<<<<<<`.

Прилагаемый HTML-прототип задаёт раскладку и визуальный стиль. Воспроизводи его, а не придумывай свой дизайн.

**Почему системный git, а не libgit2/`git2-rs`.** Пользовательские хуки, SSH-агент, credential helpers, GPG-подпись, `.gitattributes`, LFS и конфиг работают так, как привык пользователь, только если вызывается настоящий git. libgit2 допустим позже как оптимизация для чтения (например, граф истории), но **не** как основа.

**Требования к окружению.** При старте приложение проверяет `git --version` (минимум 2.30). Если git не найден — понятный экран с инструкцией и кнопкой «Указать путь к git». На Windows ищи `git.exe` в `PATH`, затем в `C:\Program Files\Git\cmd`. На Linux учти, что Tauri использует WebKitGTK, на Windows — WebView2: напиши в README о системных зависимостях.

## 5. Слой запуска git (самое важное место)

Все вызовы git идут через **один** модуль `runner.rs`. Нигде больше `Command::new("git")` не встречается.

**Обязательные правила запуска:**

- Аргументы передаются **массивом**, никогда одной строкой и никогда через shell. Пути к файлам всегда после `--`.
- Окружение для каждого вызова: `GIT_TERMINAL_PROMPT=0` (иначе git зависнет, ожидая ввода пароля), `GIT_PAGER=cat`, `LC_ALL=C` (стабильный вывод для парсеров), `GIT_OPTIONAL_LOCKS=0` для **всех операций чтения** (фоновое обновление статуса не должно захватывать `index.lock` и ломать пользователю его собственные команды).
- Флаги конфигурации: `-c core.quotepath=false`, `-c color.ui=false`, для diff — `--no-ext-diff --no-color`.
- На Windows процесс запускается с флагом `CREATE_NO_WINDOW` (`0x08000000`, через `std::os::windows::process::CommandExt::creation_flags`), иначе при каждой команде будет мигать консоль.
- Вывод читается как **байты**, затем `String::from_utf8_lossy`. Не предполагай, что весь вывод валидный UTF-8 (имена файлов, коммиты со старыми кодировками).
- Таймауты: чтение — 30 с, запись — 120 с, fetch/pull/push — без жёсткого таймаута, но с возможностью отмены из UI. При отмене процесс убивается вместе с дочерними (на Windows — через job object или `taskkill /T`).
- Результат: `{ stdout, stderr, exit_code, duration_ms }`. Ошибка git (код ≠ 0) превращается в `AppError { kind, message, details }`, где `kind` определяется по тексту stderr: `Conflict`, `DirtyWorkingTree`, `AuthFailed`, `NotARepo`, `LockFile`, `NetworkUnavailable`, `Unknown`.
- **Очередь записи.** Операции, меняющие репозиторий (stage, commit, checkout, merge, rebase, stash, …), выполняются строго по одной на репозиторий (мьютекс). Чтение может идти параллельно. Это исключает гонки за `index.lock`.
- Если появился `index.lock`: не удаляй его молча. Покажи пользователю: «Другой процесс git работает с репозиторием. Если уверен, что это не так — удалить блокировку?» — и только по подтверждению.
- Для долгих операций (clone, fetch, push) стримь прогресс через `tauri::ipc::Channel`, парси `--progress` из stderr.
- Для больших выводов (log, diff) не накапливай всё в памяти: читай поток построчно/порциями.

## 6. Парсинг вывода git

Парсеры — **чистые функции** `&[u8] → структуры`, без запуска процессов. Для каждого есть фикстуры в `tests/fixtures/`, снятые с реальных репозиториев, включая «грязные» случаи.

### 6.1. Статус

Команда: `git status --porcelain=v2 -z --branch` (для ускорения на больших репозиториях добавь `--untracked-files=normal`).

Формат записей (разделитель — NUL):

- `# branch.oid <hash>`, `# branch.head <name>`, `# branch.upstream <name>`, `# branch.ab +<ahead> -<behind>` — заголовки.
- `1 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <path>` — обычное изменение.
- `2 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <X><score> <path>` и **следующая NUL-запись — исходный путь** (переименование/копирование). Частая ошибка — не прочитать вторую запись.
- `u <XY> <sub> <m1> <m2> <m3> <mW> <h1> <h2> <h3> <path>` — конфликт.
- `? <path>` — неотслеживаемый, `! <path>` — игнорируемый.

`XY`: X — состояние индекса, Y — рабочего дерева. Файл может быть одновременно в «индексе» и «не в индексе» (частично добавленный) — в UI он должен появляться в обоих списках.

### 6.2. История

Команда: `git log -z --date-order --format=<формат> -n 500 [--skip N] <ref…>`, формат с разделителями `%x1f` между полями и NUL между коммитами. Поля: хеш, родители, имя автора, email, дата (`%at`, unix-время), имя коммитера, `%D` (ссылки), тема `%s`, тело `%b`.

Обязательные случаи для тестов: пустое тело, многострочное тело, эмодзи и кириллица в теме, merge-коммит с двумя родителями, root-коммит без родителей, коммит с octopus-слиянием (3+ родителя).

### 6.3. Алгоритм графа (lanes)

Граф вычисляется на фронтенде в `lib/graph.ts` чистой функцией. Состояние — массив `lanes[]`, где `lanes[i]` — хеш коммита, которого «ждёт» i-я колонка (или `null`, если колонка свободна).

Для каждого коммита сверху вниз:

1. Найди все колонки, ожидающие этот хеш. Первая из них — колонка коммита. Остальные «сходятся» в него (рисуются линии слияния и колонки освобождаются). Если таких нет — возьми первую свободную колонку (новая ветка).
2. Первому родителю присвой ту же колонку: `lanes[col] = parents[0]`. Если родителей нет — колонка освобождается.
3. Остальным родителям: если какая-то колонка уже ждёт этот хеш — нарисуй линию к ней; иначе займи свободную колонку (или добавь новую справа).
4. Результат для строки: колонка точки, список проходящих вертикалей, список входящих и исходящих диагоналей, цвет по номеру колонки.

**Пагинация:** состояние `lanes[]` должно сохраняться между страницами, иначе при подгрузке линии «разрываются». Храни его в сторе истории.

### 6.4. Diff

Парсер unified diff обязан корректно обрабатывать: заголовки `diff --git`, `index`, `old mode/new mode`, `similarity index`, `rename from/to`, `Binary files … differ`, `\ No newline at end of file`, пустые файлы, удаление и создание файлов, подмодули (`Subproject commit`), символические ссылки, окончания строк CRLF (не обрезай `\r`, помечай их в UI), файлы с табами и очень длинными строками.

Структура результата: `File { oldPath, newPath, status, isBinary, hunks[] }`, `Hunk { oldStart, oldLines, newStart, newLines, header, lines[] }`, `Line { kind: ctx|add|del, oldNo?, newNo?, text, noEol? }`.

### 6.5. Ссылки

`git for-each-ref --format=<…> refs/heads refs/remotes refs/tags` с полями: `%(refname)`, `%(objectname)`, `%(upstream:short)`, `%(upstream:track)`, `%(HEAD)`, `%(creatordate:unix)`, `%(*objectname)` (для аннотированных тегов). Имена веток могут содержать `/`, юникод и точки; никогда не режь их регулярками «по слешу» без учёта префиксов `refs/heads/`, `refs/remotes/<remote>/`.

### 7.1. Staging по hunk и по строкам

Это место, где модели чаще всего ошибаются. Алгоритм:

1. Из распарсенного diff возьми заголовок файла (`diff --git`, `---`, `+++`) и нужные hunk'и.
2. Для частичного выбора строк: невыбранные `+` строки удаляются из hunk'а, невыбранные `-` строки превращаются в контекстные (с пробелом в начале).
3. Пересчитай счётчики в заголовке `@@ -a,b +c,d @@` или используй `--recount` (используй оба: пересчитывай и передавай флаг).
4. Если у исходной строки был маркер `\ No newline at end of file`, он должен остаться сразу за своей строкой.
5. Патч передаётся через stdin, окончания строк сохраняются как есть.
6. Для staging берётся diff «рабочее дерево → индекс», для unstaging — «индекс → HEAD», и применяется с `--reverse`.
7. Тесты: файл с CRLF, файл без финального перевода строки, выбор одной строки из середины hunk'а, два соседних hunk'а, новый файл (`--intent-to-add`), удаление файла.

## 8. Определение состояния репозитория

Состояние определяется **по файлам в git-каталоге**, а не по предположениям. Путь к файлам получай через `git rev-parse --git-path <имя>` (это корректно работает с worktrees и подмодулями):

- `MERGE_HEAD` → идёт merge.
- `rebase-merge/` или `rebase-apply/` → идёт rebase (внутри — `head-name`, `onto`, `msgnum`, `end` для индикатора «шаг 3 из 7»).
- `CHERRY_PICK_HEAD` → cherry-pick; `REVERT_HEAD` → revert.
- `BISECT_LOG` → bisect (достаточно показать баннер, без UI).

В верхней части окна отображается баннер состояния с кнопками «Продолжить» и «Отменить» (`--continue` / `--abort`). Баннер нельзя скрыть, пока состояние активно.

| XY | Смысл | Интерфейс |
|---|---|---|
| `UU` | изменено с обеих сторон | Трёхпанельный редактор |
| `AA` | добавлено с обеих сторон | Трёхпанельный (base пуст) |
| `DU` / `UD` | удалено нами / ими, с другой стороны изменено | Выбор: «Оставить файл» или «Удалить файл», с просмотром изменённой версии |
| `AU` / `UA` | добавлено только одной стороной | Выбор: оставить или удалить |
| `DD` | удалено с обеих сторон | Подтверждение удаления |
| бинарный | любой вид | Выбор «Наша версия» / «Их версия» (`git checkout --ours/--theirs -- <path>`) |

### 9.2. Источник данных

- Версии файла: `git show :1:<path>` (base, может отсутствовать), `:2:<path>` (ours), `:3:<path>` (theirs).
- Маркеры: разбирай рабочий файл с маркерами `<<<<<<<`, `=======`, `>>>>>>>` и, если присутствует, `|||||||` (стиль diff3). Парсер должен поддерживать оба стиля, CRLF, пустые стороны и несколько конфликтов в одном файле. Маркер считается маркером, только если стоит в начале строки и за ним пробел или конец строки.
- Если нужен base для отображения, а в файле стиль не diff3, возьми его из stage 1.
- Кнопка «Перегенерировать конфликт» (`git checkout --conflict=diff3 -- <path>`) стирает ручные правки — перед ней обязателен диалог-предупреждение.

### 9.3. Критически важно: «наше» и «их» при rebase

При `git merge` «ours» — текущая ветка, «theirs» — вливаемая. При **`git rebase` и `git cherry-pick` смысл обращён**: «ours» — ветка, на которую перебазируют (upstream), а «theirs» — **ваши коммиты**, которые применяются. Из-за этого пользователи постоянно выбирают не ту сторону.

Поэтому в UI **не используй слова «ours/theirs»** без пояснения. Подписывай панели реальными именами:

- «Текущая ветка (`main`)» и «Вливаемая (`feature/diff-view`)» для merge;
- «Основа (`origin/main`)» и «Ваш коммит: `7be02d4 Add diff renderer`» для rebase и cherry-pick.

Логика кнопок («Взять левое/правое») должна учитывать тип операции и самостоятельно сопоставлять стороны.

### 9.4. Поведение редактора

- Три панели: левая сторона, правая сторона, результат. Над ними — навигация «предыдущий / следующий конфликт», счётчик «2 из 5».
- Каждый конфликтный блок имеет действия: «Взять левое», «Взять правое», «Обе (левое, затем правое)», «Обе (правое, затем левое)», «Откатить блок». Результат остаётся полностью редактируемым вручную.
- Блок считается решённым, когда в результате нет маркеров в его области. Статус каждого блока хранится явно.
- Кнопка «Отметить файл решённым» доступна, только когда в результате нет ни одного маркера. Если пользователь вручную оставил строку, похожую на маркер, — предупреждение.
- Запись результата: во временный файл рядом + атомарное переименование; сохраняются **исходные окончания строк**, кодировка, финальный перевод строки и права доступа файла. Затем `git add -- <path>`.
- Автоматически разрешай блоки, где обе стороны внесли идентичные изменения (с пометкой в UI).
- Undo/redo в результате обязателен (встроенная история CodeMirror).
- После последнего решённого файла появляется панель «Все конфликты решены» с кнопкой «Продолжить» (merge/rebase/cherry-pick) и редактируемым сообщением коммита. Продолжение запускается с `GIT_EDITOR=true`, чтобы git не пытался открыть редактор.
- «Отменить» (`--abort`) доступна всегда, с подтверждением.
- Во время rebase после каждого шага статус пересчитывается: могут появиться новые конфликты на следующем коммите. Показывай «Шаг 3 из 7».

## 10. Интерактивный rebase

Чтобы управлять `git rebase -i` без текстового редактора, задай переменные окружения `GIT_SEQUENCE_EDITOR` и `GIT_EDITOR` указывающими на **маленький вспомогательный исполняемый файл** (можно сам бинарник приложения с флагом `--rebase-helper`), который копирует подготовленный приложением todo-файл на место того, что открыл бы git. Не полагайся на shell-скрипты: на Windows это ненадёжно, а путь с пробелами нужно корректно экранировать.

UI: список коммитов с перетаскиванием, выпадающий выбор действия (`pick`, `reword`, `squash`, `fixup`, `drop`), предпросмотр итоговой цепочки. Для `reword` — отдельный диалог сообщения для каждого коммита (через `GIT_EDITOR`-помощника). Любое переписывание опубликованных коммитов сопровождается предупреждением.

## 11. Безопасность и защита данных

**Действия, требующие подтверждения (модальное окно, где написано, что будет потеряно):** `reset --hard`, discard изменений, `clean`, удаление ветки с неслитыми коммитами, force push, amend опубликованного коммита, rebase опубликованных коммитов, drop stash, удаление `index.lock`.

Дополнительно:

- Перед опасной операцией сохрани ссылку для восстановления: покажи в toast «Отменить» с командой восстановления через reflog (например, `git reset --hard ORIG_HEAD`) где это применимо.
- Force push — только `--force-with-lease`, и кнопка недоступна для веток по умолчанию (`main`, `master`) без отдельного подтверждения.
- Права Tauri (`capabilities/`) — только необходимые. Плагин shell не подключается; все вызовы git идут через собственные Rust-команды. Пути, пришедшие с фронтенда, канонизируются и проверяются: каталог должен быть репозиторием (`git rev-parse --show-toplevel`).
- CSP в `tauri.conf.json` — строгая, без `unsafe-eval`. Никаких `dangerouslySetInnerHTML` с содержимым репозитория: имена файлов, сообщения коммитов, содержимое diff — всегда как текст.
- URL remote могут содержать логин и пароль: маскируй в UI и логах (`https://***@host/…`). Приложение не хранит пароли, авторизацию выполняет git.
- Настройки и список недавних репозиториев хранятся в каталоге конфигурации приложения (через API Tauri), а не в каталоге репозитория.
- Логи по умолчанию не содержат содержимого файлов и сообщений коммитов.

## 12. Фронтенд: состояние и обновление

- **Источник правды — git.** Никакого оптимистичного обновления UI «как будто получилось»: после каждой операции перечитывай затронутые срезы состояния.
- **Файловый вотчер** (`notify`) следит за `.git/HEAD`, `.git/index`, `.git/refs/**`, `.git/MERGE_HEAD` и т. п., а также за рабочим деревом (с учётом `.gitignore` через crate `ignore`; не следи за `node_modules`, `target`, `.git/objects`). События объединяются с задержкой 150–250 мс и превращаются в одно событие `repo:changed { scopes: [status|refs|history|state] }`. События, вызванные самим приложением во время его же операции, подавляются.
- **Срезы стора:** `repo` (путь, имя, состояние), `status`, `refs`, `history` (страницы + состояние lanes), `selection`, `ui` (тема, ширины панелей, активный вид), `operations` (очередь, прогресс, ошибки).
- **Виртуализация:** список коммитов и длинные diff'ы всегда виртуализированы. Размер строки истории фиксированный (34 px).
- **Лимиты diff:** файл больше 1 МБ или больше 5 000 строк diff'а — свёрнут за кнопкой «Показать всё»; бинарные файлы — заглушка с размером; изображения — предпросмотр «до/после» (позже).
- **Выбор и фокус** сохраняются после обновлений (если коммит или файл ещё существует).
- Все асинхронные вызовы имеют состояния loading / error / empty. Пустые состояния подсказывают действие («Нет изменений. Внесите правки в рабочем каталоге — они появятся здесь»).

## 16. Типичные ошибки — чего НЕ делать

1. Не склеивай команду в одну строку и не вызывай через shell — только массив аргументов.
2. Не забывай `--` перед путями: файл с именем `-rf` или `HEAD` не должен интерпретироваться как опция или ссылка.
3. Не используй `git commit -m` с пользовательским текстом — только `-F -`.
4. Не разбирай человеко-читаемый вывод (`git status` без `--porcelain`, `git log` без `--format`). Парси только машинные форматы.
5. Не забывай `-z` там, где имена файлов могут содержать пробелы, кавычки и переносы.
6. Не читай вывод как «всегда UTF-8».
7. Не вызывай фоновые чтения без `GIT_OPTIONAL_LOCKS=0`.
8. Не запускай параллельно две операции записи в одном репозитории.
9. Не забывай про вторую запись у переименований в `status --porcelain=v2 -z`.
10. Не теряй состояние lanes при пагинации графа.
11. Не используй «ours/theirs» в UI без пояснения: при rebase смысл обращён.
12. Не завершай merge/rebase без проверки, что нет оставшихся маркеров и неразрешённых файлов.
13. Не показывай «успех», пока git не вернул код 0 и состояние не перечитано.
14. Не блокируй UI-поток: все вызовы асинхронны, с индикатором и отменой для долгих.
15. Не вставляй содержимое репозитория в HTML как разметку.
16. Не меняй пользовательский git-конфиг без явного согласия.
17. Не предполагай ветку `master` или `main` и remote с именем `origin`: читай реальные имена.
18. Не обрезай `\r` в CRLF-файлах и не «нормализуй» окончания строк при записи.
19. Не показывай огромные diff'ы целиком — лимиты и «Показать всё».
20. Не пиши код под одну ОС: пути (`\` и `/`), регистр имён файлов, запуск процессов — проверяй на всех трёх.
21. Не добавляй зависимости без обоснования и без указания версии.
22. Не оставляй `unwrap()` и `expect()` в боевом коде Rust — только корректная обработка ошибок.

## 18. Контекстные меню

### 18.1. Общие принципы

Правый клик по любому значимому элементу приложения открывает **собственное** контекстное меню, а не меню браузерного движка (там «Назад», «Обновить», «Сохранить как…», «Проверить» — такого в десктопном приложении быть не должно).

1. Один глобальный обработчик `contextmenu` на корне приложения. Он вызывает `preventDefault()` и ищет ближайший элемент с атрибутами `data-ctx="<тип>"` и `data-id="<идентификатор>"`. Если такого нет — открывается меню «пустой области» своего раздела либо ничего, но **нативное меню браузера не показывается нигде**.
2. **Исключение — редактируемые поля** (`input`, `textarea`, редактор CodeMirror): там показывается собственное меню с пунктами «Вырезать / Копировать / Вставить / Выделить всё» (и «Отменить / Повторить»), оформленное в нашем стиле. Работает и с клавиатурными сочетаниями.
3. В релизной сборке инструменты разработчика отключены. Пункт «Проверить элемент» допустим только в debug-сборке и только с зажатым Shift.
4. Меню строится **декларативно**: для каждого типа сущности есть чистая функция `buildMenu(target, repoState, selection) → MenuItem[]`. Она не вызывает git и не трогает DOM, поэтому легко тестируется. Тяжёлые проверки (например, «опубликован ли коммит») запускаются при открытии меню асинхронно: пункт сначала показывается неактивным с индикатором, потом обновляется.
5. Все действия из меню идут **той же дорогой**, что и кнопки: через команды Tauri и очередь операций из раздела 5. Никакой отдельной логики «для меню».
6. Перед выполнением действие получает идентификаторы (хеш, имя ветки, путь), а не ссылки на объекты в памяти: после обновления состояния объекты могут устареть. Перед запуском проверь, что цель ещё существует.

### 18.2. Модель пункта меню

```
MenuItem =
  | { type: 'item', id, label, icon?, shortcut?, danger?, disabled?, disabledReason?,
      checked?, children?: MenuItem[], run?: (ctx) => Promise<void> }
  | { type: 'separator' }
  | { type: 'header', label }        // необязательный неактивный заголовок группы
```

- `disabled` пункты **не скрываются**, а серятся, с пояснением «почему недоступно» во всплывающей подсказке («Нельзя удалить текущую ветку»). Скрывать пункт можно только если он вообще не имеет смысла для типа элемента.
- `danger` — опасные пункты окрашены в цвет `--del`, стоят **последней группой** меню, и всегда проходят через диалог подтверждения из раздела 11.
- Пункты, требующие ввода (имя ветки, тега, сообщение), заканчиваются многоточием «…» и открывают модальную форму.
- Подсказка с горячей клавишей справа, если у действия она есть.

### 18.3. Поведение компонента `ContextMenu`

**Позиционирование.** Меню появляется у курсора. Если не помещается справа или снизу, раскрывается влево или вверх (flip); никогда не выходит за границы окна (clamp); если слишком высокое — получает прокрутку. Подменю открываются вправо, при нехватке места — влево.

**Закрытие.** По `Esc`, клику вне меню, прокрутке любого контейнера (важно для виртуализированных списков), изменению размера окна, потере фокуса окном, выбору пункта и открытию другого меню. Одновременно открыто только одно меню (и цепочка его подменю).

**Клавиатура.** `↓/↑` — перемещение (по кругу), `Home/End` — первый/последний, `Enter`/`Space` — выполнить, `→` — открыть подменю, `←` — закрыть подменю, первая буква — переход к пункту, `Esc` — закрыть. Открытие меню с клавиатуры: `Shift+F10` и клавиша «Menu» на выбранном элементе; позиция — рядом с элементом. Для macOS: `Ctrl+клик` также открывает меню. После закрытия фокус возвращается на элемент, с которого меню было открыто.

**Доступность.** Роли `menu`, `menuitem`, `menuitemcheckbox`, `separator`; `aria-disabled`, `aria-haspopup`, `aria-expanded` для подменю. Подменю открываются с задержкой около 150 мс при наведении, чтобы не «схлопываться» при движении мыши по диагонали.

**Оформление** в стиле приложения: фон `--bg2`, граница 1 px `--line`, радиус 8 px, отступы пунктов 6×12 px, высота пункта 28 px, шрифт 13 px, без теней (допустима тонкая граница), пункт под курсором или клавиатурным фокусом — `--sel`. Анимация появления не дольше 100 мс и отключается при `prefers-reduced-motion`.

**Выделение и мультивыбор.** ПКМ по уже выделенному элементу действует на всё выделение. ПКМ по невыделенному — сначала выделяет его (сбрасывая прежнее выделение), затем открывает меню. Если действие не применимо к нескольким элементам, пункт неактивен с пояснением.

### 18.4. Состояния, влияющие на меню

Каждый `buildMenu` учитывает:

- текущая ветка и состояние `detached HEAD`;
- идёт ли merge / rebase / cherry-pick / revert (во время операции недоступны checkout, pull, создание коммитов, переключение веток; остаются «Продолжить», «Пропустить» (`rebase --skip`), «Отменить»);
- есть ли у ветки upstream и сколько коммитов впереди/позади;
- «грязное» рабочее дерево (для checkout и pull — предложить stash);
- опубликован ли коммит (есть ли он в `git branch -r --contains <hash>`) — для перезаписи истории (amend, reword, drop, interactive rebase, reset) показывать предупреждение;
- merge-коммит (для cherry-pick и revert требуется `-m <родитель>`: показывать диалог выбора родителя);
- root-коммит (нет родителя: нельзя «сравнить с родителем», revert и blame на предыдущую ревизию недоступны);
- репозиторий без коммитов;
- защищённые ветки (`main`, `master`, `develop` по умолчанию, список в настройках): force push и удаление требуют отдельного подтверждения;
- платформа: «Показать в Проводнике» (Windows) / «Показать в Finder» (macOS) / «Показать в файловом менеджере» (Linux).

## 18.5. Каталог меню по типам элементов

Команды git приведены как ориентир; детали и флаги проверяй по документации (`git help <команда>`).

### Коммит (список истории)

| Группа | Пункт | Условие / команда |
|---|---|---|
| Навигация | Checkout этого коммита | `git switch --detach <hash>`; при «грязном» дереве — предложить stash |
| | Создать ветку отсюда… | `git switch -c <name> <hash>`; имя проверять через `git check-ref-format --branch` |
| | Создать тег… ▸ Лёгкий / Аннотированный | `git tag <name> <hash>` / `git tag -a -m <msg> <name> <hash>` |
| Применение | Cherry-pick | `git cherry-pick <hash>`; для merge-коммита — выбор родителя (`-m`); недоступен для коммитов, уже входящих в текущую ветку |
| | Revert | `git revert --no-edit <hash>`; для merge-коммита — выбор родителя |
| | Создать fixup-коммит из индекса | `git commit --fixup=<hash>`; доступен только если в индексе есть изменения; опционально «и сразу применить» через `rebase -i --autosquash` с `GIT_SEQUENCE_EDITOR=true` |
| Перезапись | Изменить сообщение… | Для HEAD — `commit --amend`, для остальных — reword через interactive rebase |
| | Rebase текущей ветки на этот коммит | `git rebase <hash>` |
| | Interactive rebase отсюда… | Открывает редактор из этапа 8 |
| Сравнение | Сравнить с рабочим деревом | diff коммит ↔ рабочий каталог |
| | Сравнить с HEAD / с родителем | |
| | Выбрать для сравнения / Сравнить с выбранным | Работает как два шага; при выделении двух коммитов — «Сравнить эти два» |
| Копирование | Копировать ▸ SHA (полный), SHA (короткий), Сообщение, Автор, Тему | Через clipboard API |
| Remote | Открыть на сервере | Только если URL remote распознан (GitHub, GitLab, Bitbucket, Gitea) |
| Опасные | Reset текущей ветки сюда ▸ Soft / Mixed / Hard | `git reset --soft/--mixed/--hard <hash>`; **Hard — danger + подтверждение**; в подтверждении показать, сколько коммитов и файлов будет потеряно |
| | Удалить коммит (drop) | Через interactive rebase; danger; предупреждение, если коммит опубликован |

**Мультивыбор коммитов:** «Cherry-pick выбранных» (в правильном порядке — от старых к новым), «Squash выбранных…» (только подряд идущие, не на опубликованных ветках без подтверждения), «Копировать SHA», «Сравнить» (ровно два).

### Локальная ветка (сайдбар и чипы в графе)

| Группа | Пункт | Условие / команда |
|---|---|---|
| Навигация | Checkout | Недоступно для текущей ветки |
| | Создать ветку отсюда… | |
| Интеграция | Merge в текущую ▸ Обычный / `--no-ff` / `--squash` / `--ff-only` | Недоступно для текущей; во время merge/rebase недоступно |
| | Rebase текущей на эту | |
| | Interactive rebase текущей на эту… | |
| | Checkout и rebase на текущую | Двухшаговое действие, подтвердить |
| Remote | Fetch | |
| | Pull | Только для текущей ветки с upstream |
| | Push / Push… | Если upstream нет — «Push и установить upstream» (`-u`) |
| | Установить upstream… / Убрать upstream | `--set-upstream-to`, `--unset-upstream` |
| Сравнение | Сравнить с текущей | Показывает `A..B` и `B..A` (ahead/behind) |
| Граф | Показать только эту ветку / Скрыть на графе | Влияет на фильтр истории |
| Прочее | Переименовать… | `git branch -m` (если есть remote — предупредить о последствиях) |
| | Копировать имя | |
| | Открыть на сервере / Создать pull request | URL по шаблонам хостингов, если распознан |
| Опасные | Force push (`--force-with-lease`) | danger; для защищённых веток — двойное подтверждение |
| | Удалить | `-d`; если ветка не слита — предупреждение со списком коммитов и вариант `-D`; текущую удалить нельзя |
| | Удалить ещё и на remote… | `git push <remote> --delete <name>`; danger |

### Удалённая ветка (`origin/…`)

Checkout (создать локальную с отслеживанием: `git switch --track`), Merge в текущую, Rebase текущей на неё, Создать ветку отсюда…, Сравнить с текущей, Копировать имя, Открыть на сервере; опасное: «Удалить на remote…».

### Remote, тег, stash

- **Remote:** Fetch, Fetch с prune, Изменить URL…, Копировать URL (с маскированием логина/пароля при показе), danger: Удалить remote.
- **Тег:** Checkout, Создать ветку отсюда…, Push тега, Копировать имя, Показать сообщение (для аннотированного); danger: Удалить локально / Удалить на remote.
- **Stash:** Применить (`apply`), Применить и удалить (`pop`), Создать ветку из stash (`git stash branch`), Показать diff, Копировать сообщение; danger: Удалить (`drop`). Если применение вызвало конфликт — перейти в редактор конфликтов.

### Файл в списке изменений

Все пункты применяются ко всему выделению.

| Состояние файла | Пункты |
|---|---|
| Не в индексе | Добавить в индекс; Сбросить изменения (danger); Добавить в stash только этот файл (`git stash push -- <path>`); История файла; Blame |
| Неотслеживаемый | Добавить в индекс; Добавить в `.gitignore` ▸ этот файл / по расширению / папку; Удалить файл (danger, `git clean -f -- <path>`) |
| В индексе | Убрать из индекса; История файла; Blame |
| Конфликтный | Открыть в редакторе конфликтов; Взять версию ▸ с реальными именами сторон (см. 9.3, **не** писать «ours/theirs» без пояснения); Отметить решённым; Открыть во внешнем merge-инструменте |
| Любой | Открыть во внешнем редакторе; Показать в Проводнике/Finder/файловом менеджере; Копировать путь ▸ относительный / абсолютный; Копировать имя файла |

Если файл **уже отслеживается**, «Добавить в `.gitignore`» не сработает: предложи одновременно выполнить `git rm --cached -- <path>` и объясни причину в диалоге.

### Файл внутри коммита

Открыть diff; История файла (`--follow`); Blame на этом коммите; Открыть версию файла на этом коммите (только просмотр); Сохранить версию как…; «Восстановить файл из этого коммита» (`git restore --source=<hash> -- <path>`, danger — перезапишет рабочую копию); Копировать путь; Показать в Проводнике (если файл существует в рабочем дереве).

### Diff: блок (hunk) и строки

Добавить блок в индекс / Убрать блок из индекса; Добавить выделенные строки в индекс / Убрать; Сбросить блок или выделенные строки (danger); Копировать блок как патч; Копировать выделенный текст; Открыть в редакторе на этой строке. Пункты staging доступны только в режиме «рабочее дерево» и «индекс», но не в просмотре коммита.

### Строка в blame

Показать коммит; Копировать SHA; «Blame предыдущей ревизии» (`git blame <hash>^ -- <path>`, недоступно для root-коммита); Открыть на сервере.

### Блок конфликта (в редакторе)

Взять левое; Взять правое; Лево → право; Право → лево; Откатить блок; Копировать левое / правое. Подписи — как в разделе 9.3.

### Прочие места

- **Пустая область списка истории:** Fetch; Обновить; Перейти к HEAD; Перейти к коммиту…; Колонки ▸ (автор, дата, хеш, ссылки — с галочками).
- **Заголовок списка:** то же меню «Колонки».
- **Секции сайдбара (Ветки, Remote, Теги, Stash):** Создать…; Свернуть/Развернуть все; Обновить.
- **Название репозитория в шапке:** Показать в Проводнике; Открыть в терминале; Копировать путь; Недавние ▸; Закрыть репозиторий.
- **Баннер состояния (merge/rebase):** Продолжить; Пропустить коммит (только rebase); Отменить (danger).
- **Поле сообщения коммита:** стандартное редактирование; «Подставить сообщение последнего коммита»; «Очистить».
- **Вкладки/панели:** Закрепить; Закрыть другие (если реализованы вкладки репозиториев).

### 18.6. Диалоги, которые нужны меню

Создание ветки (имя, стартовая точка, галочка «Сразу переключиться»), создание тега (имя, аннотация), переименование, выбор режима reset, выбор родителя для merge-коммита, настройки merge, установка upstream (выбор remote и ветки), подтверждение опасных действий. Общие правила: `Enter` — подтвердить, `Esc` — отмена, фокус в первом поле, валидация имени «вживую» (через `git check-ref-format`, проверка занятости), понятное сообщение об ошибке под полем, кнопка подтверждения неактивна, пока форма невалидна.

### 18.7. Дополнительно: подсказка с командой

Внизу окна — тонкая строка состояния. При наведении или клавиатурном фокусе на пункте меню в ней показывается точная команда git, которая будет выполнена (например, `git reset --hard 7be02d4`). Это помогает понять, что делает действие, и быстрее ловит ошибки.

### 18.8. Типичные ошибки именно в меню — чего НЕ делать

1. Не оставлять нативное меню в каких-либо областях, кроме отдельно оформленных полей ввода.
2. Не отключать `contextmenu` на полях ввода без замены — иначе нельзя вставить текст правой кнопкой.
3. Не открывать меню за пределами окна и не закрывать его при прокрутке виртуального списка — типичная ошибка.
4. Не хранить в замыкании пункта ссылку на объект коммита или ветки: используй идентификатор и перепроверяй актуальность.
5. Не показывать пункты, невозможные в текущем состоянии, как активные (удалить текущую ветку, merge ветки саму в себя, cherry-pick уже примёнённого коммита).
6. Не выполнять `reset --hard`, discard, drop, force push, удаление веток и тегов без подтверждения.
7. Не использовать «ours/theirs» в подписях без пояснения.
8. Не забывать про `-m` для merge-коммитов при cherry-pick и revert.
9. Не перезаписывать опубликованную историю без предупреждения.
10. Не писать в `.gitignore` для уже отслеживаемых файлов без `git rm --cached`.
11. Не допускать, чтобы ПКМ по невыделенному элементу действовал на старое выделение.
12. Не забывать клавиатурный доступ и возврат фокуса после закрытия меню.
13. Не вешать обработчики на каждую строку списка: один делегированный обработчик на корне.
14. Не вызывать git при построении меню синхронно. Вычисляй асинхронно и обновляй пункты.
